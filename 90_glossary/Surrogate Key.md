# Surrogate Key

> [!eli5] Summary
> A surrogate key is an ID number the system assigns to each row, separate from real-world values like email addresses or product codes. It stays stable even when the real-world values change.

**In data work:** A **natural key** comes from the business, such as a customer's email or a supplier's product code. Natural keys change, collide across systems, and can be long strings. A surrogate key is a meaningless value, usually a `BIGINT`, that the warehouse assigns. In a [[Star Schema|star schema]], [[Dimension Table|dimension tables]] use surrogate keys and [[Fact Table|fact tables]] store them as [[Primary and Foreign Keys|foreign keys]]. With [[Slowly Changing Dimensions|type 2 slowly changing dimensions]], each version of a customer gets its own surrogate key, so a sale links to the customer's address at the time of the sale.

**In Databricks:** Generate surrogate keys with identity columns:

```sql
CREATE TABLE shop.gold.dim_customer (
  customer_sk BIGINT GENERATED ALWAYS AS IDENTITY,
  email STRING,
  city STRING
);
```

- `GENERATED ALWAYS` rejects explicit values; `GENERATED BY DEFAULT` accepts them, which helps when migrating existing IDs.
- Values are unique and increasing but not guaranteed to be consecutive.
- Identity columns must be `BIGINT`, and Databricks advises using them only where concurrent writes to the table are not needed.
- A full rebuild of the table can assign different IDs, so use identity keys on tables that are appended to, not recreated.

Where a deterministic key is needed, a hash of the natural key (for example, `xxhash64`) is an alternative.

Seen in: [[Primary and Foreign Keys]], [[Star Schema]], [[Slowly Changing Dimensions]]
